## Architecture Decision V18.6.3 — TEST ONLY
Implement a disposable **PostgreSQL 17** synthetic schema `v1863_qa` in an ephemeral GitHub Actions job. `qa/store-authority-v1863/pg17-fixture.sql` creates synthetic tenants, stores and memberships under a composite `(tenant_id, store_id)` key, plus products, orders and page connections. One tenant contains both Store A and Store B. Synthetic `tenants` is RLS-protected too, and no role can list another tenant through the tenant table. Synthetic Owner A and Owner B each have access to only their store; a second tenant has Store C. Staff cannot read private orders. Expired/revoked members lose access. A competing Page connection violates a scoped active-Page uniqueness rule. Authenticated actors get SELECT grants only; writes are denied.

Use PostgreSQL's actual RLS evaluation with `SET LOCAL ROLE v1863_authenticated` and a **synthetic** `request.jwt.claim.sub` input for tests. This simulates an already-authenticated context. It does **not** verify Supabase JWT integrity, browser sessions, canonical real membership, Meta OAuth, or a production adapter. The JWT claim must be generated by a trusted authentication component in a real integration; this harness does not create an authenticated service.

A real implementation will need canonical `stores` and `store_memberships`, unambiguous Store selection via trusted server-side session, composite foreign keys on all store-owned tables, per-Store RLS including SELECT/UPDATE/DELETE coverage, customer isolation and Page registry in backend-only schema. It must ensure existing tenant legacy data and workflows are migrated without collisions or backdoor access. This proposal **must not** automatically migrate Supabase staging or publish Messenger/n8n.
